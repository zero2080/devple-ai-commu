배포 파이프라인 준비 (D1단계)

devple-ai-commu · 2026-10-01 (2026-10-02 갱신 — PR #1) · 작성: Claude Code · 근거: docs/DEPLOYMENT.md 1.1 (chat), handoff 2026-10-01-deployment-pipeline

결론. Commu 화면(https://stories.devple.net/commu/)을 ArgoCD 자동 배포에 넣기 위한 프론트 쪽 준비를 마쳤어요. 운영 이미지, nginx 설정, k8s 매니페스트, CI 배포 잡이에요. 이미지를 로컬에서 빌드·실행해 경로 규칙과 헤더를 모두 확인했어요. 브라우저로 열어서 CSP 위반이 없는 것도 확인했어요. 클러스터·Cloudflare·GitHub 설정은 제가 건드리지 않았고, 아래 순서대로 직접 해 주셔야 해요.

6해 주실 일
27초로컬 이미지 빌드
13/13경로 규칙 확인
0CSP 위반 (Report-Only)

0. 해 주실 일 (순서대로)

  1. PR #1 머지 — 배포 잡이 든 .github/workflows/ci.yml 변경은 PR #1로 올라가 있어요(2026-10-02 갱신: 토큰에 workflow 권한이 생겨 브랜치 chore/ci-deploy-job을 푸시했고, PR의 CI check는 운영 빌드·Mock 배제 검사까지 통과). 머지하면 check가 통과한 뒤 deploy 잡이 이미지를 GHCR에 올리고 k8s/deployment.yaml 태그를 커밋해요. ArgoCD 앱을 아직 적용하지 않았으니 클러스터에는 아무 일도 일어나지 않아요.
  2. main 브랜치 보호 — main에 보호 규칙이 있으면 deploy 잡의 태그 커밋(github-actions[bot])이 막혀요. 켜져 있다면 봇 푸시를 허용해 주세요. 없으면 할 일이 없어요.
  3. GHCR 패키지 확인 — 첫 배포 뒤 ghcr.io/zero2080/devple-commu-web 패키지가 생겨요. 클러스터의 ghcr-secret 토큰이 이 패키지를 받을 수 있어야 해요(read:packages). 패키지가 비공개로 만들어졌는지 공개인지는 확인하지 못했어요(추정, 정확도 중간 — 같은 계정이라 ghcr-secret으로 받을 수 있을 것으로 봐요).
  4. ArgoCD 앱 1회 적용 — kubectl apply -f k8s/argocd/application.yaml. 저장소가 공개라 ArgoCD 자격 증명은 필요 없어요. 확인: ArgoCD devple-commu-web이 Synced/Healthy, kubectl -n devple get pods에 devple-commu-web-* Ready, 기존 devple-api·devple-commu에 영향 없음. 클러스터 안에서 /healthz 200, /commu 301, /commu/x → index.html, /·/api/x 404 (DEPLOYMENT 7장)
  5. Cloudflare 규칙 (서버 S10 뒤) — Tunnel → Public Hostname에서 stories.devple.net의 기존 Stories 규칙보다 위에 두 개를 추가해요. ① path ^/api/v1/ → http://devple-commu.devple.svc.cluster.local:8080 ② path ^/commu(/|$) → http://devple-commu-web.devple.svc.cluster.local:80. 시험 기간에 Cloudflare Access를 건다면 경로(/commu, /api/v1)에만 걸어요. 호스트명 전체에 걸면 Stories가 막혀요.
  6. 공개 뒤 확인과 CSP 강제 전환 — https://stories.devple.net/commu/ 로그인 → 새로고침해도 로그인 유지 → 월드 진입 → 개발자 도구에 CSP 위반이 없는지 봐 주세요. 위반이 없다고 알려 주시면 Content-Security-Policy-Report-Only를 강제(Content-Security-Policy)로 바꿀게요. Stories 화면(/user/reset-password 등)이 그대로 동작하는지도 확인해 주세요.

1. 만든 것

파일내용
Dockerfile, .dockerignoreNode(.nvmrc 24와 일치 검사)·pnpm(packageManager)으로 운영 빌드(VITE_MOCK=false, VITE_API_BASE_URL=/api/v1) → Mock 검사 → 비루트 nginx(nginx-unprivileged:1.30-alpine, 8080). 화면 파일은 /commu/ 아래. .env(로컬 Mock 설정)는 빌드에 들어가지 않아요
nginx/default.conf, security-headers.conf/commu → /commu/(상대 주소 리다이렉트), 해시 파일 1년 캐시, 그 밖 no-cache, 없는 정적 파일 404, 화면 경로는 index.html, /healthz 200, /·/api/* 등 나머지 404, gzip, 보안 헤더·CSP는 /commu/ 응답에만
k8s/devple-commu-web Deployment(1개, 무중단 교체, ghcr-secret, 프로브, 10m/32Mi·128Mi, 비루트)·Service(80 → 8080), kustomization(네임스페이스 리소스 없음), ArgoCD Application(알림 어노테이션은 devple-stories와 같게, CreateNamespace 없음)
.github/workflows/ci.ymlcheck에 운영 빌드 + Mock 검사 추가. deploy 잡(main 푸시만): GHCR 로그인 → amd64·arm64 이미지 :<sha7>·:latest → 태그 커밋. k8s/만 바뀐 푸시는 CI를 다시 돌리지 않아요
앱 코드운영 빌드 기준 경로 /commu/(라우터 basename), Mock 워커 파일을 운영 빌드에서 삭제, pnpm check:dist(Mock 흔적 검사), zod jitless(아래 2-1)

2. 진행 중 발견한 것

문제처리
2-1. CSP 위반 1건: 이미지를 브라우저로 열어 보니, 검증 라이브러리 zod가 처음 검증할 때 new Function으로 eval이 되는지 시험했어요. 예외는 삼키지만 CSP(script-src 'self')에는 위반으로 보고돼요. 강제 모드로 바꾸면 콘솔이 오염됐을 거예요앱 진입점에서 가장 먼저 zod jitless를 켜서 시험을 건너뛰게 했어요(zod 소스 주석이 권하는 방법). 다시 확인하니 위반 0이에요
2-2. 404 응답에도 1년 캐시 헤더가 붙음캐시 헤더는 성공 응답에만 붙게 고쳤어요
2-3. 클러스터 아키텍처를 모름 — GitHub 러너는 amd64라, 클러스터가 arm64(예: Apple Silicon·라즈베리파이)면 이미지가 돌지 않아요amd64·arm64 둘 다 만들어요. 빌드는 러너에서 한 번만 하고, nginx 단계만 아키텍처별로 만들어 에뮬레이션 없이 빨라요(추정, 정확도 중간 — 클러스터는 확인하지 않음)

4. 알아 둘 점

  • 개발 URL과 운영 URL이 달라요: 개발 서버·E2E는 localhost:5173/, 운영은 /commu/ 아래예요(DEPLOYMENT가 프론트 재량으로 둔 부분, ARCHITECTURE 9장에 기록). 기준 경로 차이로 생길 문제는 운영 이미지 스모크로 확인해요.
  • 서버(Commu API)가 아직 없어서, 배포해도 지금은 로그인 화면까지만 동작해요(/api/v1/auth/refresh 404). Cloudflare 규칙을 넣기 전에는 외부에서 보이지 않아요.
  • 서버가 보낸 정보(2026-10-01-server-session-fyi)의 제안 — 탭 두 개가 동시에 refresh할 때 진 탭이 로그아웃되지 않도록 refresh 401에 한 번 더 시도 — 은 이어서 반영해요.
